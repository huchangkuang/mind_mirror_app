## Context

`mind_mirror_app` 需要从当前空白/基础状态快速迁移到可上线 MVP，且必须复用与 Web 相同的后端接口（`mind_mirror_api`），避免服务端分叉。移动端与 Web 在 UI 层可以分离，但业务语义、鉴权规则、错误码处理与核心流程必须保持一致。

约束包括：
- 首期同时覆盖 iOS/Android，优先保证核心路径稳定可用。
- 认证体系需要满足移动端安全存储与自动续期（`refreshToken` 安全存储，401 自动刷新，失败清理登录态）。
- 业务包含多流程页面（介绍/答题/结果/历史）和用户资料管理，涉及跨模块状态共享。

## Goals / Non-Goals

**Goals:**
- 建立 Expo + React Native 工程基础，形成可持续迭代的目录与模块边界。
- 建立统一 API 客户端与鉴权中间层，确保 Web 与 App 接口契约一致。
- 完成认证、测评（MBTI/城市匹配）、个人中心三大业务域 MVP 闭环。
- 建立可观测与质量基础：统一错误处理、基础测试、Sentry 接入点。

**Non-Goals:**
- 不做推送、离线缓存、复杂动效、A/B 实验、深度埋点平台接入。
- 不追求 Web 与 App 共用 UI 组件，仅共用逻辑与契约思路。
- 不在本期改造后端接口协议。

## Decisions

### 决策 1：采用 Expo + expo-router 作为应用壳与导航方案
- **选择**：使用 Expo 管理构建与运行环境，使用 `expo-router` 做文件路由。
- **原因**：降低跨平台基建成本，路由结构与页面组织天然契合业务分层。
- **备选**：裸 RN + react-navigation。放弃原因是初期基建与原生配置成本更高，不利于 MVP 速度。

### 决策 2：API 层采用“同构契约 + 移动端适配”的分层
- **选择**：在 `src/api/` 建立请求实例、拦截器、错误映射与 endpoint 封装；业务模块只调用 domain API 方法。
- **原因**：屏蔽平台差异（存储、网络异常、重试策略），同时保持与 Web 接口参数/返回结构一致。
- **备选**：在各 feature 内直接请求。放弃原因是重复逻辑多，难以统一鉴权与错误策略。

### 决策 3：鉴权使用 accessToken + refreshToken，配单飞刷新锁
- **选择**：
  - `accessToken` 放内存状态（必要时持久化短期缓存）；
  - `refreshToken` 存 `expo-secure-store`；
  - 401 触发刷新，刷新请求采用单飞锁（同一时刻仅一次刷新），其余请求等待结果；
  - 刷新失败统一登出并清理状态。
- **原因**：兼顾安全性、稳定性与并发一致性。
- **备选**：每个请求独立刷新。放弃原因是会产生刷新风暴和竞态覆盖问题。

### 决策 4：状态管理与服务端状态分离
- **选择**：`zustand` 管本地会话与 UI 状态；`react-query` 管服务端数据缓存、失效与重取。
- **原因**：降低全局状态复杂度，提升列表/历史等接口型页面的可维护性。
- **备选**：全部放 Zustand 或 Redux。放弃原因是服务端数据生命周期管理成本较高。

### 决策 5：按业务域拆分 feature 包
- **选择**：`src/features/auth`、`src/features/mbti`、`src/features/city-match`、`src/features/profile`，每个域包含 `api`、`hooks`、`screens`（或页面逻辑）与 `types`。
- **原因**：迁移阶段可并行推进，减少跨域耦合，便于后续与 Web 逻辑对照。
- **备选**：按技术层统一目录。放弃原因是跨功能追踪成本高。

## Risks / Trade-offs

- **[Risk] 接口语义与 Web 端实现存在隐性差异** → **Mitigation**：先整理 endpoint 映射清单并做联调冒烟用例，差异统一在 `src/api/adapters` 收敛。
- **[Risk] Token 刷新并发导致登录态抖动** → **Mitigation**：实现刷新单飞锁 + 请求重放队列 + 失败兜底登出。
- **[Risk] 多流程问卷页面状态复杂，容易出现回退错乱** → **Mitigation**：每个流程建立独立状态机（当前题号、答案草稿、提交态），统一从 hook 暴露操作。
- **[Risk] Expo 生态与原生依赖兼容性问题** → **Mitigation**：首批仅引入 MVP 必需依赖，并在 iOS/Android 真机各做一轮安装与构建验证。

## Migration Plan

1. 搭建基础工程骨架与目录结构，接入路由、状态管理、请求层与 SecureStore。
2. 完成鉴权链路（登录/注册/登出、token 存储、自动刷新、失败清理）。
3. 迁移测试列表与 MBTI 全流程（介绍、答题、结果、历史）。
4. 迁移城市匹配全流程（介绍、答题、结果、历史）。
5. 迁移个人中心（昵称修改、密码修改、历史摘要）。
6. 接入 Sentry 与基础测试，执行冒烟回归并准备发布。

回滚策略：
- 采用 feature flag 或版本开关（如有）控制入口曝光；
- 任一核心流程阻塞时可回退到仅开放登录与只读能力版本；
- 保持后端接口零变更，避免服务端回滚依赖。

## Open Questions

- 历史摘要在个人中心展示的数据粒度是否与 Web 完全一致，是否需要分页策略？
- 城市匹配题目资源是否需要预加载优化（若题量大，可能影响首屏时延）？
